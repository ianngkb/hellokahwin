## Part 1: the standard (brain/docs/regression-testing.md)
# Regression testing — the standard for every repo

Ian, 2026-11-04: "Apply this across the board as part of our process."

A regression is a thing that used to work and quietly stopped, because of a
change made somewhere else. Agents write almost all of the code here and
nobody reads every diff, so the tests are the only thing standing between "fixed
X" and "fixed X, broke Y". This page is the rule. The skills point at it.

## The three layers

Every repo has all three. A repo missing one is on the rollout table below
until it has it.

### 1. A change never ships without its own test — and a bug fix never ships without the bug's test

- Every new behaviour gets a test that **fails with the change reverted**
  (already `autopilot/build.md` §3).
- **Every bug fix starts by writing the test that reproduces the bug**, watches
  it fail, then fixes the code until it passes. That test stays in the suite
  forever. This is the actual mechanism that stops a bug coming back; the other
  two layers only notice that something broke.
- `/urgent` may defer that test, never drop it: it lands in the post-deploy
  review (§5 of `/urgent`) or the urgent ship is not closed.

### 2. Before every ship: the WHOLE suite, not the touched part

`/buildit` runs the repo's full unit/integration suite on the integrated batch,
on every profile — not only type-check and build. Old tests are the regression
tests; running only the new ones checks nothing old.

- **Compare against the baseline, don't demand perfection.** Run the suite on
  `origin/main` (the last thing that shipped) as well as on the batch. A test
  that was already red on `origin/main` is recorded as *pre-existing* in the
  ship report and does not block. **A test that is green on `origin/main` and
  red on the batch is a regression and blocks the ship** — FAIL → STOP, exactly
  like a broken build.
- Read the test COUNT, never just the exit code (`0 total` exits 0).
- CI runs the same suite on every pull request and every push to `main`, as a
  hard gate.

### 3. After every deploy: a standing smoke suite against the live site, automatically

A smoke suite is a short browser/HTTP test run against production that proves
the important pages and endpoints still work: they load, nothing 5xx's, the
key forms still validate, background services answer their health check.

- **It runs by itself**, as the last job of the repo's deploy workflow, after
  the deploy succeeds. Not "the operator runs it", not "the spec names it" —
  a suite that waits for someone to remember it rots unseen (buddy, 2026-11-04:
  10 of 40 checks had been failing for weeks because nothing ran them).
- **Read-only, or it names its cleanup.** It never writes real customer data.
  Data it depends on (a test booking page, a test tenant) is a *fixture*:
  written down in the spec's header with how to recreate it.
- **It grows.** When a shipped spec's prod check (`V-P…`) is repeatable and
  read-only, the ship worker adds it to the standing suite in the same run, so
  next month's deploy re-checks this month's feature. One-off checks that are
  never re-run catch nothing the second time.
- **Red does not roll back.** It means "production is live and something on it
  looks wrong". The deploy run goes red, GitHub emails the pusher, and
  `/buildit` (which watches the run with `--exit-status`) reports a failed
  ship.
- **It must be green before it can gate.** When switching a suite on for the
  first time, run it by hand against production first. Fix or remove the
  failures before wiring it in; a check that is always red trains everyone to
  ignore it.

## What a repo records

`CLAUDE.md` or `docs/verify.md` names, for that repo:

- the full-suite command (layer 2) and roughly how long it takes;
- the smoke-suite command and where it runs (layer 3);
- the fixtures the smoke suite needs, and how to recreate them;
- what the suite does **not** cover (usually: anything behind sign-in, until a
  saved signed-in session exists for it).

+/**
+ * Standing smoke suite — layer 3 of the regression-testing standard
+ * (brain/docs/regression-testing.md).
+ *
+ * Proves the live site still works after a deploy: the important pages load,
+ * nothing answers 5xx, the database is reachable, the signed-out admin lock
+ * holds, and the analytics collector is up.
+ *
+ * WHERE IT RUNS: automatically, by .github/workflows/smoke-production.yml,
+ * when Vercel reports a successful Production deployment to GitHub. By hand:
+ *
+ *     node --test scripts/smoke-prod.mjs
+ *     SMOKE_BASE_URL=https://example.vercel.app node --test scripts/smoke-prod.mjs
+ *
+ * READ-ONLY. Every request is a GET, except one POST of a deliberately invalid
+ * body to the analytics collector, which is rejected with 400 before anything
+ * is stored (src/app/api/v1/analytics/collect/route.ts validates the body
+ * first). No customer data is written, so there is nothing to clean up.
+ *
+ * FIXTURES: none. The article and category it opens are picked from the live
+ * sitemap on each run, so it needs no test rows in the production database.
+ * It does need the site to have at least one published article in a
+ * category, which is the site's real content, not a fixture.
+ *
+ * NOT COVERED: anything behind sign-in (/admin/*, the editor, uploads), draft
+ * previews (need a share token), and what pages look like (no browser).

+import { test, before } from 'node:test';
+import assert from 'node:assert/strict';
+
+const BASE = (process.env.SMOKE_BASE_URL || 'https://hellokahwin.com').replace(/\/+$/, '');
+const UA = 'hellokahwin-smoke/1.0 (+https://github.com/ianngkb/hellokahwin)';
+const TIMEOUT_MS = 20_000;
+
+async function get(path, init = {}) {
+  const url = path.startsWith('http') ? path : `${BASE}${path}`;
+  const res = await fetch(url, {
+    redirect: 'manual',
+    signal: AbortSignal.timeout(TIMEOUT_MS),
+    ...init,
+    headers: { 'user-agent': UA, ...(init.headers || {}) },
+  });
+  const body = await res.text();
+  return { url, status: res.status, headers: res.headers, body };
+}
+
+function expectOk(r) {
+  assert.equal(r.status, 200, `${r.url} answered ${r.status}, expected 200`);
+}
+
+let articleUrl;
+let categoryPath;
+
+before(async () => {
+  const r = await get('/sitemap.xml');
+  expectOk(r);
+  const locs = [...r.body.matchAll(/<loc>([^<]+)<\/loc>/g)].map((m) => m[1].trim());
+  // /artikel/<category>/<slug> — an article detail page.
+  const articles = locs.filter((u) => /\/artikel\/[^/]+\/[^/]+$/.test(new URL(u).pathname));
+  assert.ok(articles.length > 0, 'sitemap lists no article pages');
+  // Sitemap URLs are absolute on the canonical host; re-root them on BASE so a
+  // run against a preview URL tests that deployment, not production.
+  articleUrl = `${BASE}${new URL(articles[0]).pathname}`;
+  categoryPath = new URL(articles[0]).pathname.split('/').slice(0, 3).join('/');
+});
+
+test('home page loads with the site title', async () => {
+  const r = await get('/');
+  expectOk(r);
+  assert.match(r.body, /<title>[^<]*HelloKahwin/, 'no HelloKahwin <title> on /');
+  assert.match(r.body, /href="\/artikel\/[^"]+"/, 'home page links to no articles');
+});
+
+test('sitemap.xml lists the site', async () => {
+  const r = await get('/sitemap.xml');
+  expectOk(r);
+  const count = (r.body.match(/<loc>/g) || []).length;

+});
+
+test('robots.txt keeps admin out of search and points at the sitemap', async () => {
+  const r = await get('/robots.txt');
+  expectOk(r);
+  assert.match(r.body, /Disallow: \/admin\//);

+test('article index /artikel loads', async () => {

+});

+test('an article page renders its content, structured data and share image', async () => {

+  expectOk(r);
+  assert.match(r.body, /<h1[\s>]/, `no <h1> on ${articleUrl}`);

+  return {

+    clerkMiddleware: () => (req: NextRequest) => {
+      clerkHandled(req.nextUrl.pathname);
+      return new Response(null, { status: 299, headers: { 'x-test': 'clerk' } });

+  };

+const { default: middleware } = await import('../middleware');
+
+function run(path: string) {
+  const req = new NextRequest(new URL(path, 'https://hellokahwin.com'));
+  return middleware(req, {} as NextFetchEvent) as Response;
+}
+
+const isClerk = (res: Response) => res.headers.get('x-test') === 'clerk';
+const isRewrite = (res: Response) => res.headers.has('x-middleware-rewrite');

+describe('middleware — the admin sign-in gate', () => {
+  it.each([
+    '/admin',
+    '/admin/articles',
+    '/admin/site-analytics',
+    '/login',
+    '/no-access',
+    '/api/v1/inspire/upload',
+  ])('hands %s to Clerk', (path) => {
