## 2. The two things the brief got wrong

Reported plainly, because the brief asked for exactly this.

### 2a. The 3,040 ms baseline is a COLD cache, not a warm one

The brief states **"Measured FCP 3,040 ms with a warm cache on a fast
connection."** Warm cache is not reproducible anywhere near that number.

| condition                               | FCP                |
| --------------------------------------- | ------------------ |
| article, warm cache                     | **124 ms**         |
| article, cold browser cache, CDN `HIT`  | 172–304 ms         |
| article, cold browser cache, CDN `MISS` | **1,140–1,304 ms** |
| article, cold + slow lambda start       | **2,816 ms**       |

The 3,040 ms is real — I reproduced 2,816 ms — but it is a **cache MISS**, not a
warm load. Twenty runs, from `fcp-vs-cache.mjs`, each a fresh browser context so
the payload is byte-identical every time:

```
run  cache        age   ttfb  docEnd    fcp   jsEnc  url
  0 MISS             0     15    1179   1304  177894  /artikel/…/adat-hantaran-berbeza-negeri
  1 HIT              2     15      91    204  177894  /artikel/…/adat-hantaran-berbeza-negeri
  0 MISS             0     15    1008   1140  177894  /artikel/…/hantaran-tempah-atau-buat-sendiri
  1 HIT              1     14      88    204  177894  /artikel/…/hantaran-tempah-atau-buat-sendiri
```

Look at the last two columns together. **`jsEnc` is identical — 177,894 bytes —
in every single run, while FCP swings from 204 ms to 1,304 ms.** FCP tracks
`x-vercel-cache`, and `docEnd` (the document finishing) accounts for ~90 % of it
on a MISS.

**So the JavaScript payload is not what sets FCP on this site.** The blocking
dependency, named as the DoD requires: **server-side page generation on a CDN
cache MISS.** Reducing JavaScript cannot move a number the JavaScript is not
setting — which is why the audit below reports honest small wins rather than
claiming an FCP improvement it did not cause.

### 2b. "542 KB of JavaScript" is the uncompressed figure; the wire cost is a third of it

|                  | files | over the wire (encoded) | uncompressed (decoded) |
| ---------------- | ----- | ----------------------- | ---------------------- |
| brief's figure   | 14    | —                       | 542 KB                 |
| measured, before | 16    | **177,894 B (174 KB)**  | 570,086 B (557 KB)     |
| measured, after  | 14    | **166,414 B (163 KB)**  | 531,967 B (520 KB)     |

The 542 KB is close to the _decoded_ total. Readers download **174 KB**. The
brief's framing overstates the network cost by 3.2×. Both numbers are worth
knowing — decoded is what the phone must parse, encoded is what it must fetch —
but they are not interchangeable, and the payload was described as if the larger
one were the download.

### The drop that shipped

`<Toaster />` was mounted in the **root** layout, so sonner shipped to every
article and every card grid. Audited by grepping every `from 'sonner'` import in
the codebase: **all 18 call sites are under `(admin)` or in admin-only
components** (media manager, tiptap node views, the article editor). Not one
public surface can raise a toast.

Moved to `(admin)/layout.tsx`. The root layout already did exactly this for
`ClerkProvider` and the console webfonts — the precedent and its reasoning were
already written in that file; the Toaster had simply never been held to it.

Measured on production, before → after: **16 files → 14, 177,894 → 166,414 B
encoded (−11,480), 570,086 → 531,967 B decoded (−38,119).**

### The defer that did not ship, and why

**PhotoGallery (29,946 B decoded / 11,190 B encoded) — DEFER is correct but
blocked by its own API.** The lightbox takes its trigger as a prop and renders
it:

```tsx
<PhotoGallery images={galleryImages} trigger={<span>Lihat semua foto (N)</span>} />
```

So `next/dynamic({ ssr: false })` would remove the "Lihat semua foto" pill from
the server HTML and pop it in after hydration — trading 11 KB for a visible
layout shift on the cover, on the exact surface UX-01 just spent an item
protecting. **The blocking dependency: the trigger must be lifted out of the
component before the modal can be split.** That is an API inversion, not a
config change, and it is larger than this item's DoD. Parked with the reason,
not silently dropped.

**tailwind-merge (27,555 B decoded) — KEEP, blocked.** It is `cn()`, called by
the shadcn primitives that the client components are built from. Removing it
means removing runtime class merging from every client component. Not
independently droppable.

**The framework floor is 462,301 B decoded / 143,048 B encoded** — React,
react-dom and the six Next runtime chunks. That is 81 % of the payload and it is
not application code. After the sonner drop, application JavaScript on a public
page is **~62 KB decoded**: the gallery, the nav, the mobile bar, two error
boundaries and next/image.

## 5. How it was built

**`articles.cover_image_lqip text`** — a new nullable column, not a key inside
`cover_image_variants`. That JSONB is iterated as `Record<string, {url}>` in six
places (`Object.keys(newVariants) as (keyof ImageVariants)[]`, the R2 key
collector in `backfill-media.ts`, the image-quality toolbar); a string-valued key
would have broken every one. An additive column touches none of them.

**One resolution order, three copies, all commented.** The placeholder must be
derived from the _same_ crop the card renders — `next/image` paints it with the
same `object-fit`, so a placeholder from a different crop is confidently the
wrong colours in the wrong corners. `crop-4x3-article-card` → `variants.low` →
`coverImageUrl` appears in `article-card.tsx`, `lib/storage/lqip.ts` and
`scripts/backfill-cover-lqip.mts`, each carrying a comment naming the other two.

**Null is a supported state everywhere.** `generateLqipFromUrl` returns null
rather than throwing, every component spreads the props conditionally, and a
missing placeholder degrades to the pre-UX-04 flat plate. A cover upload never
fails because a placeholder could not be produced.

**Three write paths keep it current** — both regenerate actions and the normal
editor save (which re-derives whenever the cover moved, so swapping a cover can
never leave the previous photograph's colours blurred under the new one) — plus
`scripts/ingest-article.mts` for new content.

### Production writes, in order

1. `ALTER TABLE "articles" ADD COLUMN "cover_image_lqip" text;` — verified
   `is_nullable: YES`, additive, applied **before** the deploy so the
   then-current code was unaffected.
2. `pnpm backfill:lqip --db <prod>` — dry-run first (86 would-write, 0 failed),
   then for real: **wrote 86, skipped 0, failed 0**.
3. Deploy `0d4f6fd`, then `c414f98`.

## Retrospective

### What we learned that is not written down anywhere

**FCP on this site is set by the CDN cache state, not by the payload.** This is
the single most useful thing measured today and it exists nowhere in the repo. It
means a whole class of future performance work — bundle splitting, tree shaking,
dependency pruning — cannot move FCP, and anyone who tries will burn an item
proving it again. The evidence is the twenty-run table in §2a: byte-identical
JavaScript, FCP swinging 204 ms → 1,304 ms, tracking `x-vercel-cache`.

**A performance number without its cache state is not a measurement.** The brief
said "warm cache" and meant cold. Both of us would have been right about our own
number and wrong about each other's. Warm was 124 ms; the reported figure was
3,040 ms. That is a 25× disagreement produced entirely by an unstated condition.

**And a payload number without its compression state is not one either** — 542 KB
decoded is 174 KB on the wire, and the item was scoped as if readers downloaded
the larger figure.

### What we did twice

**Written a throwaway measurement rig.** UX-01 wrote `measure.mjs` into its
EVIDENCE folder yesterday. I wrote `measure-perf.mjs`, `fcp-vs-cache.mjs`,
`timeline.mjs` and `filmstrip.mjs` into mine today, and re-derived UX-01's
playwright-core + system-Chrome launch incantation from scratch to do it. Two
items, two private rigs, zero shared tooling — and the _reason_ the brief's
baseline was wrong is that there was no shared rig to state its conditions.

### What we nearly shipped, and what caught it

**A placeholder derived from the wrong crop.** The first design derived the LQIP
from the original full-frame image. It would have looked fine in review and
subtly wrong in production on every off-centre smart crop — a blur whose colours
disagree with the photograph replacing it, which is worse than the flat plate
because it is confidently wrong rather than obviously absent. What caught it was
writing down _why_ `next/image` paints the placeholder with the image's own
`object-fit` before writing the code.

**A flat plate left behind on the read-next bar.** I would have reported "cards
and covers done" and been wrong. What caught it was filming production _after_
the ship instead of trusting the local result — 8 of 11 blurred, and I made
myself name all three stragglers instead of rounding up. Two were UX-02's; one
was mine, and `c414f98` fixed it.

### Which document must change, and who owns the edit

1. **`scripts/measure-page.mjs` — NEW, owned by me, made below.** The rig is
   promoted out of an EVIDENCE folder into `scripts/`, wired as `pnpm
perf:measure`, with the cache-state finding written into its header where the
   next person measuring will actually read it. It reports `x-vercel-cache`
   beside every FCP **by default**, so the next performance number physically
   cannot be quoted without its cache state attached. This is the edit that stops
   §2a happening again, and it is the one I can make.

2. **The sprint tracker's UX-04 row — owned by the CEO, not me.** Its baseline
   reads "FCP 3,040 ms with a warm cache". It is a cold-cache MISS. I have not
   touched it: a DoD is never rewritten after the sprint starts, and the tracker
   is not mine to edit. Flagged here for `/endsprint`.

3. **`src/components/inspire/article-card.tsx` — owned by me, already done.** The
   `cardImageUrl` resolution order is now load-bearing in three files. All three
   carry a comment naming the other two, so the next person to change one is told
   what breaks.
