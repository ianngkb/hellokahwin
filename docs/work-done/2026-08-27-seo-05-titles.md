## The `seo_title` drift audit — every field, all 69 articles

**CLAIM.** Exactly one `seo_title` had drifted from its H1. The audit's real
finding is somewhere else entirely, and it is much worse.

**EVIDENCE.** All 69 published rows, read from production 2026-08-26T17:05Z
(`docs/work-done/2026-08-27-seo-05-titles-EVIDENCE/seo-title-drift-audit.json`):

| | count |
| --- | --- |
| published articles | 69 |
| `meta_title` IS NULL | **40** |
| `meta_title` set (all 29 legacy WordPress imports) | 29 |
| - identical to the H1 after brand-strip | 28 |
| - **drifted from the H1** | **1** (`mas-kahwin-ikut-negeri`) |
| rendered title >= 60 chars, before this item | **69 of 69** |
| `meta_description` that is a truncated body fallback ending in an ellipsis | **28** |

Three findings, in ascending order of importance.

**1. The drift count is one.** The brief expected "at least one, total
unknown". It is exactly the one already identified. No hidden stale field.

**2. Forty articles have no SEO title at all, structurally.** Their title is
the H1 verbatim plus the brand. `scripts/ingest-article.mts:810-856` never
writes `meta_title` — not on insert, not in its `ON CONFLICT DO UPDATE` — so
there is no way to give an ingested article a shorter title than its H1. A
useful side effect: **`meta_title` written by hand survives a re-ingest, while
`meta_description` does NOT** (the upsert overwrites it from the file). All five
articles changed here are legacy WordPress imports with no source file, so
neither is at risk today.

**3. Twenty-eight meta descriptions are not descriptions.** They are the first
~140 characters of the article body, cut mid-sentence at an ellipsis — "…Banyak
dewan komuniti dan…", "…Ramai pasangan terburu-buru…". Four of the five fixed
here were among them. **Twenty-four remain.** Not opened; it is a content pass,
not a title pass, and it should be sized on its own.

## What the audit actually found: 39 of 69 articles were serving the WRONG TITLE

**CLAIM.** While auditing the field, the live check found that **39 of 69
published articles were serving the root layout's default title and default
meta description in production** — with correct database rows and correct `<h1>`
on the same page. **And our own documented publish procedure is what causes it.**

**EVIDENCE — the census.** Sweeping all 69 canonical URLs, 2026-08-26T16:58Z,
39 returned:

```html
<title>HelloKahwin — Idea &amp; Panduan Perkahwinan Malaysia</title>
<meta name="description" content="Idea, tips dan panduan perkahwinan untuk pasangan Malaysia. Rancang majlis impian anda mengikut bajet."/>
```

That is `src/app/layout.tsx:8` — the root default — not any article's title.

**EVIDENCE — I checked whether my own load caused it, and it did not.** Fetched
sequentially, 1.2s apart, the pattern is exact: every response carrying
`x-vercel-cache: STALE` served the default title; the first response that was
not STALE served the correct one.

```
goodies-kahwin           DEFAULT/STALE  DEFAULT/STALE  own/HIT
mas-kahwin-perak         DEFAULT/STALE  DEFAULT/STALE  own/HIT
harga-sewa-dewan-kahwin  DEFAULT/STALE  DEFAULT/STALE  own/HIT
```

**MECHANISM.** `src/app/(public)/artikel/[category]/[slug]/page.tsx:429`:

```ts
try {
  pageData = await withDeadline(getArticlePageData(slug), 1_500, `inspire-article-meta:${slug}`);
} catch {
  return {};
}
```

`generateMetadata` runs under a 1.5-second deadline and returns `{}` on a miss.
Next then falls back to the root layout's metadata. **That empty result is
prerendered and cached** (`X-Nextjs-Prerender: 1`), and
`s-maxage=600, stale-while-revalidate=3000` serves it for up to an hour. A
cached failure — the same shape as the `revalidateTag(tag, 'max')` defect one
layer down.

**AND THIS IS THE PART THAT CHANGES HOW WE SHIP.** `POST
/api/cron/revalidate-content` drops the origin data cache for **every article at
once**, so every page's next render starts cold and loses the 1.5s deadline.
Measured, same afternoon:

```
before SEO-05 touched anything                            39 of 69 serving the default title
immediately after the documented revalidate-then-purge    51 of 69
```

SEO-02, SEO-06 and CONT-08 each ran that sequence this sprint. That is where
the original 39 came from. **Our publish procedure has been quietly stripping
the title off every page it touches.**

**WHAT WAS DONE ABOUT IT.** The workaround was found and proved on all 69: purge
the edge WITHOUT dropping the origin data cache first, so the re-render finds a
warm cache and wins the deadline.

```
round 1: purged 69 paths, ok=true (HTTP 200 in 5 request(s))
round 1: still default after re-render: 0

FINAL: 0 of 69 still serving the root default title
```

Census in
`docs/work-done/2026-08-27-seo-05-titles-EVIDENCE/sitewide-title-census.json`.

**WHAT WAS NOT DONE, DELIBERATELY.** The code fix. It belongs in
`src/app/(public)/artikel/[category]/[slug]/page.tsx`, which carries unmerged
commits on `ianng89/pillars-ingest-redirects` (`c4c57a9`, `baae7fe`, `f75c42f`).
Editing it from here would race another item's branch. **Open for engineering.**
Candidates: do not cache a `{}` metadata result; raise or drop the deadline; or
fall back to the article `title` from the same warm cache the page render uses.

**Until it is fixed, no publish is finished until the title has been read
back from live HTML.** A 200 and a correct row prove nothing here.

## Retrospective

**What we learned that is not written down.**

Rule 1 was never actually written down. `ceo-memory.md` referred to it as "the
averaged position below" and the file did not contain it — a forward reference
to a rule nobody had typed. It was applied twice in review and recorded zero
times, which is exactly how it came back. A cross-reference is not a record.

The bigger lesson is about where a field audit should look. The brief asked
whether any `seo_title` had drifted from its page. One had. Meanwhile 39 pages
were serving no article title at all, and the field audit could not see it,
because **the defect was between the field and the SERP, not in the field.**
A row-level check cannot see a render-level failure — the same shape as SEO-02's
lesson that a page-level check could not see a link-level `nofollow`. That
shape has now cost two sprints. The general form is worth stating: **check the
artefact the consumer receives, not the input you control.**

And a cached failure is worse than a failure. `generateMetadata` returning `{}`
under load is a reasonable fallback; freezing that `{}` into a prerender and
serving it for an hour is not.

**Which document must change, and who owns the edit.**

1. `docs/boardroom/ceo-memory.md` — **done in this item**, commit `70b8e50`.
   Owner: head-of-seo-content (this item).
2. `skillcentral/.../head-of-seo-content.md` — **done in this item**, commit
   `926c203`. Owner: head-of-seo-content. **CEO must run `install.sh`.**
3. `src/app/(public)/artikel/[category]/[slug]/page.tsx` — **NOT done, and
   deliberately not.** Owner: whoever holds `ianng89/pillars-ingest-redirects`,
   which has unmerged commits in that route. The fix is the `return {}` on
   deadline miss being cacheable.
4. **The publish runbook — no such document exists, and that is the gap.** The
   revalidate-then-purge sequence lives in `ceo-memory.md` prose and in
   `src/lib/cache/edge-purge.ts` comments, and it is WRONG in a way that has
   silently damaged three shipped items. It has been corrected in `ceo-memory.md`
   here, but a sequence this consequential should be one runbook that ingest,
   the admin editor and every content agent follow. **Owner: CEO to assign** —
   it spans engineering and editorial and belongs to neither alone.

**What we did twice.**

Measured the mas-kahwin family twice — the CEO's read and mine. That one was
worth repeating: it is the item's whole premise, and re-measuring surfaced the
rising canonical share and the year-bearing query split that the first read did
not have. Independent confirmation of a load-bearing number is not waste.

Verified the five live pages three times, and that WAS waste the first time
round. The first verification ran straight after the purge and reported all five
as failures — I read it as my write not landing, when it was the metadata
deadline firing on the cold render my own purge had caused. Purging and then
immediately measuring measures the purge, not the write.

**What we nearly shipped, and what caught it.**

Four things.

*A title item that would have shipped five wrong titles.* If the "after" check
had been "the database row is correct", all five would have been signed off
while production served the root default title. The DoD's "quoted from live HTML
before and after" caught it. That clause was the single most valuable line in
the brief.

*A finding that was partly self-inflicted.* The first sweep was six-wide
concurrent, and the honest question was whether my own load caused the timeouts.
The sequential re-check settled it: the failure tracked `x-vercel-cache: STALE`,
not concurrency. Without that check, "39 of 69" would have been an artefact
presented as a measurement.

*A claim about another team's worktree that was simply false.* I wrote into
`ceo-memory.md` that `pillars-ingest-redirects` had uncommitted work in the
article route. `git status` there shows one modified settings file. The route
has unmerged COMMITS, which is a different and weaker claim. Caught by checking
before committing; corrected in place.

*A race for `hantaran-tunang`.* It was item 3 on evidence. `ListAgents` showed a
live session on `feat/cont-05-hantaran-tunang`, and an ingest there would
overwrite `meta_description` from the file. Enumerating the sessions rather than
recalling them is what caught it — the same rule the brief gives for worktrees.

**One thing to keep that is not a lesson.** The brief said item one is
`mas kahwin ikut negeri`, not setiawangsa, and named the reason: the previous
review applied a significance test and then exempted the page it had already
built a theory around. Both of this item's rules exist to stop that, and the
arithmetic table above is there so the next reviewer can check the claim rather
than trust it.
