## The run was TWO passes, and why

The five articles cross-link each other. `scripts/ingest-article.mts` refuses a
file whose `internalLinks` or body links name a slug that is not yet a
**published** article, so no single ordering works.

- **Pass 1** (`run-pass1.ps1`, 21:38:34 → 21:41:02Z) ingested five copies with
  only the sibling links stripped, `--commit --publish`. Five exits of 0.
- **`published_at` read back** out of production and pinned into each file as
  `publishedAt:` (`publishedat.json`).
- **Pass 2** (`run-pass2.ps1`, 21:43:23 → 21:45:33Z) ingested the real files,
  cross-links restored, `--commit --update --publish`, wrapped with
  `vault.ps1 run vercel.twn -EnvVar VERCEL_TOKEN` so the edge purged. Five exits
  of 0, `Purged (HTTP 200 in 1 request(s))` on each.

The pin worked: all five `published_at` values after pass 2 are identical to the
values pass 1 wrote.

**Cost of the two-pass design, stated plainly:** every image was uploaded twice,
so this run created **32 media rows for 16 declared image slots**, and the 16
from pass 1 are now unreferenced along with their R2 objects. They are orphaned,
not harmful. Deleting object storage has no recovery path, so that stays a CEO
decision rather than something this run cleaned up.

## The generateMetadata defect, measured

Every one of the five first cold renders served the **root layout's default
`<title>`** — `HelloKahwin — Idea & Panduan Perkahwinan Malaysia` — with a
correct `<h1>` and a correct database row on the same page. This is the
`generateMetadata` 1.5s deadline miss SEO-05 flagged, and the empty result gets
cached.

What this run adds to the record:

- **A serial, paced sweep reproduced it 5 times out of 5.** Requests were 6s
  apart, one at a time. Concurrency was not required. The cold renders took
  **3.0s–6.4s**, which alone exceeds the 1.5s deadline.
- **The trigger here was another writer's ingest.** Each `--revalidate-url`
  drops the origin data cache, so pages that had just been repaired went cold
  again. Timeline: repaired at 22:05:04, the concurrent run updated rows at
  22:02:48 and 22:03:17, and the 22:05:25 census then hit cold renders and
  re-cached the bad metadata on all five. `titlecheck.json` at 22:09 shows all
  five `HIT` at `age≈230`, which is exactly that census's entries.
- **My own verification sweep re-created the defect it was measuring.** That is
  the "a `GET` published a broken page" trap from Stage 7, in a new shape:
  not a burst against cold hubs, but a *repeat census taken while someone else
  was dropping the cache*.
- **Repair is reliable once writes stop.** `heal3.mts` — purge one path, absorb
  the revalidating response, then take the honest request — fixed **5/5 on the
  first attempt** at 22:11:13–22:12:24Z, renders 340–495ms.

Each serves its own title and its own meta description. Titles include the
` | HelloKahwin` the root layout appends; the longest is 77 characters against
roughly 60 that Google prints, so three of the five will be truncated in the
SERP.

**Not fixed here, and filed as a follow-on with SEO-05.** The mechanics matter
to whoever picks it up, so they are written down rather than left to be
rediscovered:

- `scripts/ingest-article.mts` **never writes `meta_title`** — not on insert,
  not in its `ON CONFLICT`. So a hand-written short title **survives a
  re-ingest**. This is the opposite of the intuition, and I had it backwards
  when I first passed the item to SEO-05; they corrected it.
- `meta_description` is the column that **does** get overwritten from the file,
  so the file's `metaDescription` stays authoritative and must not be
  hand-edited in the database.
- The budget for a stored `meta_title` is roughly **45 characters**, because the
  root layout appends ` | HelloKahwin` and the target is under 60 for the whole
  rendered string.

The safe pattern, then: short title into `meta_title` by hand; leave
`metaDescription` to the file. Not done tonight because rewriting five titles
after the DoD is met is rewriting the item mid-sprint.
