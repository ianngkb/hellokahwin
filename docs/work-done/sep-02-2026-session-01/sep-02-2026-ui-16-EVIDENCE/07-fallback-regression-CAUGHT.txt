UI-16 — THE FALLBACK REGRESSION, and the check that caught it.
02 September 2026, ~20:30 UTC, hours after UI-16 deployed at 19:51.

WHAT HAPPENED. Six articles were re-ingested at 20:12-20:16 UTC from a checkout
predating UI-16. `processSmartCrops` REPLACES the whole `cover_image_smart_crops`
object rather than merging into it, so the `crop-4x3-article-card-md` key was
DROPPED. `resolveArticleCoverSource` then fell from the rendition straight to the
FULL `crop-4x3-article-card`.

`doa-untuk-isteri` is the proof it was RE-INGESTION and not a backlog: it was
backfilled at 20:00 and had no `-md` at 20:12. `crop-4x3-article-card-sm`
survived on all six, because that rung has been on master since Sprint 05 and the
stale checkouts carry it.

WHY NO RULE COULD SEE IT. The box is 4:3 and the file is 4:3, so `image-aspect`
reads 0. It is a downscale, so `image-upscale` reads 0. It IS a named crop, so
`shaped-slot-variant` (R2) passes. A pure byte defect has no rule behind it.

CODE FIX SHIPPED (5c79712): the resolver gains DES-18's 528px rung between the
rendition and the full crop — md -> sm -> card -> low, ordered
largest-that-is-still-BUDGETED rather than largest. `-sm` would upscale 1.43x in
this slot's 756px box on its own; it does not, because the caller caps the figure
to the asset's stored width, so the plate narrows to 528 CSS px and R1/R2/R5/R6
all stay green at 22,906 B instead of 790,000. A regression test goes RED against
the old ordering (verified by reverting the one line).

WHAT IT DOES NOT FIX: `scripts/ingest-article.mts` runs from an agent's OWN
checkout, so a publish from a stale worktree will keep dropping the key until
every worktree carries this commit. The mitigation is that the failure now costs
~23 KB an article instead of ~790 KB, and this audit names the rows to backfill.
Escalated to the owner as an ingest-architecture question; not absorbable from a
branch.
