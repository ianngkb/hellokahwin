## PLAT-11 — The ship check was WRONG on PLAT-05 and SILENT on PLAT-06

**2 points**

### Why

git merge-base --is-ancestor returns false FOREVER for a squash-merged branch, because squashing creates a new commit and the branch tip never becomes an ancestor. The CEO used it on PLAT-05 and reported SHIPPED work as UNSHIPPED. A false negative is worse than no check, because the correct response to 'unshipped' is to ship it again. On PLAT-06 the check was silent on genuinely unshipped work with a clean git status.  CARRIED FROM THE SPRINT 02 RETRO, verbatim, because the planning pass lost this detail: Sprint 02 retrospective, Murat. Two failures, and the second is the one nobody had said. (1) git merge-base --is-ancestor returned false for squash-merged PLAT-05 - a false negative that called shipped work unshipped, and it was ALREADY DOCUMENTED in startsprint/SKILL.md in capitals with a worked example, and shipped anyway. (2) It gave NO SIGNAL AT ALL on PLAT-06, which was genuinely unshipped at 6 commits unpushed and 7 ahead of main - a state where git status reads clean. A check that is wrong on the item that shipped and silent on the item that did not is not a gate; it is noise with a green tick. The false-negative direction is the dangerous one: it invites RE-shipping, and on this codebase a re-triggered revalidate re-creates a sitewide title defect within 14 minutes.

### Definition of done — verbatim, NOT negotiable

OBSERVABLE: Ancestry replaced with POSITIVE EVIDENCE: git cat-file -e origin/main:<a file the work added>. `git rev-list @{u}..HEAD` mandatory per item. Both the squash-merge false negative and the clean-status false silence reproduced against the fixed check and shown to be caught. CHECKED BY: Reproduce both real Sprint 02 cases - PLAT-05 squash-merged, PLAT-06 unshipped-with-clean-status - and show the new check returns the right answer on each. BEWARE THE FALSE PASS: Check which merge style the repo actually uses before trusting either test. EVIDENCE LANDS: docs/work-done/ entry with both reproductions.  PLUS THE CARRIED-FORWARD DoD, which is more specific than the one written at planning and is NOT superseded by it: Replace the ancestry proxy with POSITIVE evidence - gh pr view --json state,mergedAt, or grep the default branch log for the item key - and add git rev-list --count @{u}..HEAD as a MANDATORY per-item check, because unpushed is invisible to everything else. Prove both directions: show the check passing on a squash-merged branch (where merge-base returns false) and FAILING on a branch with unpushed commits (where git status reads clean). Then delete the ancestry instruction rather than leaving both in the file - a wrong check beside a right one teaches people to trust the wrong one.

## Standing rules — these bind you

- **DONE MEANS SHIPPED.** Not built, not committed, not "working locally".
  Merged to the default branch AND deployed AND visible, or ingested to
  production AND reachable. If your item's result is a document, it is
  committed and PUSHED. A file on one machine is not a deliverable.
- **Check the artefact the CONSUMER receives**, never the input you control.
  Reading your own source proves what you intended, not what shipped.
- **A status code is not a measurement.** If a check needs a header, a

  it up.
